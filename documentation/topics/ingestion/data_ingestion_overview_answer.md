### Фактор 2: Линейный рост объёма корпуса

**Корневая причина:** число чанков растёт линейно с объёмом документов; prod-архив — multi-GB, тест — ~1411 чанков.

### Фактор 3: Concurrency vs rate limit

**Корневая причина:** поставщик ограничивает параллельные запросы; default 6 → автоматическое снижение до 2; relabel использует 3.

**Рекомендуемое 80/20-решение:** **динамический планировщик** — отправлять N запросов, измерять реальную пропускную способность и адаптировать concurrency под текущий rate limit (без хардкода). Реализовать через `asyncio.Semaphore` с динамической корректировкой.

- **Effort:** S (1 день)
- **Ожидаемый выигрыш:** утилизация rate limit на 90–95% вместо текущих 60–70%.
- **Альтернатива:** увеличить `concurrency` до 10 и положиться на автоматическое снижение OpenRouter — проще, но менее предсказуемо.
- **Отложить:** полноценный брокер с очередями и приоритетами — overkill для текущего объёма.

### Фактор 4: Синхронный Neo4j dual-write

**Корневая причина:** `Semaphore(1)` сериализует запись в Neo4j, каждый `MERGE` занимает 0,8–1,0 с с учётом deadlock-retry.

**Рекомендуемое 80/20-решение:** **базовая очередь для Neo4j-записей** — складывать операции в `list` и выполнять batch-commit каждые 10–20 экспериментов (один `UNWIND`-запрос вместо N отдельных). Это снизит накладные расходы на сетевые round-trips.

- **Effort:** M (2–3 дня)
- **Ожидаемый выигрыш:** −30–40% времени ожидания Neo4j (с 0,8–1,0 с до 0,2–0,3 с на эксперимент в среднем).
- **Альтернатива:** отключить Neo4j (`USE_NEO4J=false`) и писать только в VSA — +100% скорости, но теряется граф.[не нравится]
- **Отложить:** полноценный Outbox + Redis Streams (Stage 3) — требует новой инфраструктуры.

### PPTX

**Рекомендуемый 80/20-подход:** использовать **`python-pptx`** для извлечения текста со всех слайдов. Обходить все `shapes` и собирать текст из `text_frame`.

```python
from pptx import Presentation
prs = Presentation(path)
text = "\n".join([
    shape.text for slide in prs.slides 
    for shape in slide.shapes if hasattr(shape, "text")

```

### 2.1. Асинхронная очередь Neo4j (Outbox + фоновый воркер)

#### Цель
Полностью отделить запись в Neo4j от основного потока ingestion, чтобы убрать `Semaphore(1)` и позволить LLM-обработке идти с высоким concurrency без deadlock'ов и задержек на сетевых round-trips.

#### Архитектура
- **Outbox-таблица** в SQLite (или даже в памяти с периодической записью) — хранит операции для Neo4j: создание узлов, обновление рёбер, удаление (не используется).
- **Фоновый воркер** (отдельный поток или процесс) читает из outbox пачками (например, по 50–100 записей) и выполняет один `UNWIND`-запрос на всю пачку.
- Основной поток **не ждёт** подтверждения записи в Neo4j — только складывает операцию в outbox и продолжает обработку следующего чанка.
- **Гарантии доставки**: outbox сохраняется на диск, чтобы при падении воркера данные не терялись. После успешной записи в Neo4j помечаем записи как обработанные.

#### Детали реализации
1. **Структура outbox** (SQLite):
```sql
CREATE TABLE neo4j_outbox (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    operation TEXT NOT NULL,  -- 'MERGE_NODE', 'MERGE_RELATIONSHIP'
    payload JSON NOT NULL,    -- данные узла/ребра
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    processed BOOLEAN DEFAULT FALSE
);
```

2. **Интеграция в `neo4j_graph.py`**:
   - Вместо немедленного вызова `session.run()` — вызываем `outbox.add(operation, payload)`.
   - Outbox может быть реализован как синглтон с буферизацией (например, накапливать 20 операций и сбрасывать в SQLite одним INSERT).

3. **Фоновый воркер**:
   - Запускается при инициализации приложения (или через отдельный CLI-команду).
   - Периодически (каждые 0.5–1 с или при накоплении 50 записей) забирает необработанные записи, группирует их по типу операции и выполняет batch-запросы.
   - Пример batch-запроса для узлов:
```cypher
UNWIND $batch AS item
MERGE (n:Node {id: item.id})
SET n += item.properties
```
   - После успеха помечает записи как `processed = TRUE`.

4. **Обработка ошибок**:
   - При сбое воркер логирует ошибку и повторяет попытку (с экспоненциальной задержкой) для этой пачки.
   - Если после 3 попыток ошибка сохраняется — помечает записи как `failed` и отправляет уведомление (в лог).

5. **Совместимость с kill switch** (`USE_NEO4J=false`): если Neo4j отключён, outbox не используется, все операции игнорируются.

#### Ожидаемый эффект
- Время ожидания записи в Neo4j снижается с 0,8–1,0 с до **0,05–0,1 с** на эксперимент (т.к. основной поток только ставит в очередь, а batch-запись выполняется асинхронно).
- Можно поднять `concurrency` LLM до 10–15 без риска deadlock'ов.
- Суммарное ускорение инжеста: **−70–80%** времени, ранее тратившегося на Neo4j.

#### Effort
**5–7 дней** (разработка outbox, воркера, интеграция с существующим кодом, тестирование на тестовом корпусе).

#### Риски и компромиссы
- **Задержка согласованности**: эксперимент появляется в VSA сразу, но в Neo4j — с задержкой до 1–2 с. Для текущих задач (не real-time) это приемлемо.
- **Дополнительная сложность**: необходимо следить за размером outbox (если воркер падает, очередь растёт). Нужен мониторинг.
- **Транзакционность**: если эксперимент упал после записи в VSA, но до outbox — данные в Neo4j не появятся. Это допустимо, т.к. при повторном прогоне идемпотентность восстановит.

### 2.3. Распараллеливание обработки документов (process pool)

#### Цель
Ускорить начальные этапы пайплайна — сканирование каталогов, парсинг PDF/DOCX, извлечение метаданных и чанкинг. Эти операции сейчас выполняются последовательно в рамках одного документа, что не использует все ядра CPU.

#### Архитектура
- Использовать `multiprocessing.Pool` (или `concurrent.futures.ProcessPoolExecutor`) для параллельной обработки **списка файлов**.
- Каждый воркер получает путь к файлу, вызывает `DocumentParser.parse()` и возвращает список чанков с метаданными.
- Главный процесс собирает все чанки и передаёт их в LLM-обработку (которая уже параллельна по чанкам через `concurrency`).
- Важно: параллелизм на уровне файлов **не конфликтует** с параллелизмом на уровне чанков — они работают на разных этапах.

#### Детали реализации
1. **Модификация `corpus_loader.py`**:
   - Собрать все пути к файлам (из `data/` или `test_data/`).
   - Разбить на батчи (например, по 10 файлов на воркер, чтобы уменьшить оверхед на создание процессов).
   - Использовать `ProcessPoolExecutor(max_workers=N)`, где N = число ядер CPU (или задаётся параметром `--file-workers`).

2. **Функция-воркер**:
```python
def process_file(file_path: Path) -> list[DocumentChunk]:
    parser = DocumentParser()  # создаётся внутри, чтобы избежать shared state
    return parser.parse(file_path)
```

3. **Сбор результатов**:
   - Получить список чанков от всех воркеров, объединить в один список.
   - Передать в `IngestionPipeline` (который уже обрабатывает чанки параллельно через `asyncio` или `ThreadPool`).

4. **Совместимость с идемпотентностью**:
   - Перед парсингом можно проверить, существует ли уже эксперимент для данного файла/чанка — но это лучше делать на этапе LLM, а не здесь. Парсинг всё равно нужен для метаданных.

#### Ожидаемый эффект
- Время парсинга и чанкинга сокращается на **20–30%** (особенно для больших PDF с множеством страниц).
- Для prod-архива (тысячи файлов) выигрыш заметнее, чем для тестового (15 файлов).

#### Effort
**3 дня** (изменение загрузчика, настройка пула, тестирование на разных ОС, обработка исключений в воркерах).

#### Риски и компромиссы
- **Память**: если все файлы большие, одновременный парсинг может потреблять много RAM. Ограничиваем число воркеров (например, 4) и используем батчи.
- **GIL**: парсинг PDF (PyMuPDF) и DOCX (python-docx) в основном на C, поэтому многопроцессность даёт выигрыш, но не линейный.
- **Повторное создание парсеров**: каждый воркер создаёт свой экземпляр, что увеличивает накладные расходы — но они ничтожны по сравнению с временем парсинга.
- **Обработка ошибок**: если один файл повреждён — воркер должен вернуть пустой список или выбросить исключение, которое главный процесс логирует и продолжает.

### 2.5. Валидация качества извлечения + автоисправление

#### Цель
Повысить success rate инжеста за счёт:
- отбраковки «пустых» или «бедных» экстракций (мало сущностей или связей),
- автоматического исправления типичных ошибок (например, неправильная классификация сущности),
- повторного вызова LLM с уточняющим промптом для проблемных чанков.

#### Архитектура
- После получения `NLPExtractor` результата (entities + relations) и перед записью в VSA запускается **валидатор качества**.
- Валидатор вычисляет **скоры**: количество сущностей, количество связей, наличие обязательных типов (Material, Process), согласованность связей с онтологией.
- Если скор ниже порога (например, <3 сущностей или <2 связей) — чанк помечается как `low_quality` и направляется на **повторный LLM-запрос** с изменённым промптом (акцент на поиск сущностей и связей).
- Если после повторного запроса качество не улучшилось — используется **rule-based автоисправление**:
  - Добавление пропущенных сущностей на основе ключевых слов (расширенный словарь).
  - Создание связей по шаблонам (например, если есть `Material` и `Process` в одном чанке — добавить `uses_material`).
- В крайнем случае — чанк отклоняется (не пишется в VSA), но это должно быть <1% случаев.

#### Детали реализации
1. **Метрики качества** (в `ingestion.py`):
```python
def quality_score(extraction: NLPOutput) -> float:
    n_entities = len(extraction.entities)
    n_relations = len(extraction.relations)
    has_material = any(e.type == "Material" for e in extraction.entities)
    has_process = any(e.type == "Process" for e in extraction.entities)
    # Штраф за отсутствие ключевых типов
    score = n_entities * 0.5 + n_relations * 0.3 + (1 if has_material else 0) * 2 + (1 if has_process else 0) * 2
    return score
```

2. **Повторный вызов LLM**:
   - Если `score < threshold` (например, 5), отправляем чанк снова, но в промпт добавляем инструкцию: «В этом тексте должны быть материалы и процессы. Извлеки их обязательно».
   - Можно также сменить температуру (0,7) для большей креативности.

3. **Rule-based автоисправление**:
   - Словарь ключевых слов для Material: `["сплав", "сталь", "алюминий", "титан", "уран", "плутоний", ...]`.
   - Если в тексте есть такое слово, но сущность отсутствует — создаём сущность типа Material с именем из текста.
   - Если в тексте есть глаголы действия (`"производят"`, `"обрабатывают"`, `"плавят"`) — создаём Process.
   - Затем создаём связи по умолчанию: Material → Process (uses_material), Process → Output (produces_output) — если есть соответствующие сущности.

4. **Интеграция**:
   - В `IngestionPipeline.run()` после вызова `nlp_extractor` добавляем блок валидации.
   - Если после автоисправления качество всё ещё низкое — логируем как `validation_failed` и **не пишем** в VSA (для relabel — восстанавливаем старый бэкап).
